# 文件搜索性能优化方案

**适用版本：FileDock 1.0.0**
**状态：方案评审中，尚未实施**

分析 FileDock 当前文件搜索（扫描）的性能缺陷，评估第三方库 seekr 与各平台原生索引能力，给出持久化索引的推荐架构、规模预估、实施路线与基准测试计划。

> 说明：文中的耗时、工作量均为基于经验的数量级估算，**未经实测**。最终选型以第 8 节的基准测试结果为准。

## 1. 问题定位

FileDock 的"搜索"实际分两层：

| 层 | 位置 | 行为 | 是否瓶颈 |
|---|---|---|---|
| 扫描 | [`scan.rs`](../app/src-tauri/src/scan.rs) | 每次 `list_files` 都完整遍历所有目标目录，用 glob / 正则匹配文件名 | **是** |
| 过滤 | [`FileTable.tsx`](../app/src/components/FileTable.tsx) | 前端对已取回的列表做 `name.includes(q)` | 基本不是 |

在搜索框输入不会触发文件系统操作。慢的根源是：切换分类、手动刷新、文件变化事件都会触发**全量重新遍历**。优化目标是"不要每次都遍历"，并且**重启电脑后也不需要重新索引**。

## 2. 现有实现的缺陷

### 扫描层（Rust）

1. **无缓存**：[`commands.rs`](../app/src-tauri/src/commands.rs) 的 `list_files` 每次都调用 `scan_category`，切回同一分类也要重扫。
2. **单线程遍历**：`walkdir` 串行读目录，大目录树、机械硬盘、网络盘上很慢。
3. **文件变化后全量重扫**：[`watch.rs`](../app/src-tauri/src/watch.rs) 丢弃了 notify 事件中的具体路径，只发 `files-changed(categoryId)`，前端收到后再完整调用一次 `list_files`。
4. **无剪枝**：规则只匹配文件名，递归时仍进入 `node_modules`、`.git`、系统目录等；无排除规则、无深度限制。
5. **目标目录重复遍历**：多条规则指向同一目录或互相包含时各自遍历，最后才用 `HashMap` 去重。
6. **扫描不可取消**：切换分类后旧的 `spawn_blocking` 仍会跑完，结果被前端丢弃。
7. **结果一次性返回**：UI 须等整个扫描结束；每次通过 IPC 传输完整的 `Vec<FileEntry>` JSON。
8. **错误被静默丢弃**：`filter_map(|e| e.ok())` 吞掉权限不足等错误。
9. **glob 逐个比对**：[`matcher.rs`](../app/src-tauri/src/matcher.rs) 对每个 `Pattern` 依次 `any`，可改用 `globset`（影响很小）。
10. **监听只覆盖当前分类**：`start_file_watch` 会先停掉旧的 watcher，其他分类的变化无从得知。

### 过滤层（前端）

11. 只支持文件名子串匹配；每次输入都对全部文件执行 `toLowerCase()`；排序和过滤都在 JS 中对整个数组进行。文件量达到数十万以上时会成为问题（见第 6 节）。

## 3. seekr 评估

评估对象：[muhammad-fiaz/seekr](https://github.com/muhammad-fiaz/seekr) 0.1.1（本地源码阅读，未运行）。

### 3.1 实际实现

| 模块 | 实现 |
|---|---|
| `indexer.rs` | `WalkDir` 串行遍历 + `par_bridge()`，收集后 `INSERT OR REPLACE` 批量写 SQLite |
| `database.rs` | 单张 `files` 表，时间存 RFC3339 字符串，7 个二级索引 |
| `search.rs` | SQL `LIKE '%x%'` 分别查文件名和路径，内存中过滤、打分、排序 |
| `watcher.rs` | 仅把 notify 事件转换为 `FileEvent`，**不更新索引** |
| `core.rs` | `SeekrApp` 用单个 `Mutex<Database>` + moka 缓存 |

### 3.2 自身问题

**性能**

- 遍历仍是串行的：`par_bridge()` 只并行化了条目的后续处理，读目录本身是单线程。
- `IndexerConfig.ignore_dirs` 在 `indexer.rs` 中未被使用；`ignore_patterns` 在遍历后才判断，不剪枝。
- `index_incremental` 仍遍历整棵树，只是跳过旧文件的写入，且不处理删除。
- 每次索引后都重建 TF-IDF 语义编码器（`core.rs` 的 `index_full` / `index_incremental`），需要读全表。
- `LIKE '%x%'` 无法使用索引；名称与路径合并去重是 O(n²)。
- 建索引时持有数据库大锁，阻塞所有查询。

**正确性**

- 正则搜索只检查 `get_all_files(limit*3)` 返回的前若干行（默认 1500 行）。
- 模糊搜索的候选来自 `LIKE` 子串查询，实际不具备模糊能力；分数被写死为 100。
- 搜索缓存键缺少 extension、size、sort、limit、offset、root，不同查询可能命中错误的缓存。
- `LIKE` 声明了 `ESCAPE` 但未转义输入中的 `_`、`%`。
- 默认最多返回 50 条；空查询报错，无法"列出全部"。
- 全量索引不删除已消失的文件；`remove_stale_entries` 最多检查 100,000 条。

**与 FileDock 不匹配**

- 不支持 glob（`*` 被 `LIKE` 当作普通字符）。
- `SearchQuery.root`、`recursive` 在 `search()` 中未使用，无法表达 `TargetRule`。
- `FileEntry` 缺少 `created_at` 与 `is_readonly`，而 FileDock 默认按 `createdAt` 排序。
- 默认忽略 `*.exe`、`*.dll`、`*.bin`。
- 无 feature 开关，CLI、表格、进度条等依赖全部编入；依赖 `notify 8`（FileDock 为 `notify 6`）；edition 2024 + let-chains 要求 rustc ≥ 1.88。

### 3.3 结论

| FileDock 缺陷 | seekr 能否解决 |
|---|---|
| 每次全量遍历 | ⚠️ 有持久化，但新鲜度需调用方维护 |
| 单线程遍历 | ❌ |
| 变化后全量重扫 | ❌ watcher 不写回索引 |
| 无剪枝 | ❌ |
| 不可取消 / 非流式 | ❌ |
| glob、正则、按目录与递归限定 | ❌ |
| 前端过滤能力弱 | ⚠️ 有过滤能力，但正则、模糊有 bug |

**不建议直接引入 seekr。** 可借鉴的思路只有两点：持久化索引、把 watcher 事件转换为具体的增删改（`watcher.rs` 的 `convert_event`）。若坚持使用需要 fork 并大幅修改，工作量接近重写。

## 4. 推荐架构：持久化索引

基于 `walkdir`/`ignore` + `notify` + SQLite 自行实现，覆盖 Windows、macOS 以及将来可能的 Linux。

### 4.1 存储选型

| 方案 | 结论 |
|---|---|
| 整份快照文件（原子写入） | 10 万文件约 20MB，每次变化重写整份，不可行 |
| 快照 + 追加日志 + 压缩 | 需自行实现崩溃恢复与压缩 |
| **SQLite（`rusqlite` bundled，WAL）** | **推荐**：增量写入便宜、事务、崩溃可恢复；安装包约 +1MB |
| `redb` | 可行，但需自行维护按目录、按规则的二级索引 |

数据库位置：`%APPDATA%\FileDock\index.db`（macOS 为对应的配置目录）。

### 4.2 表结构（草案）

```
meta     (schema_version)
targets  (target_id PK, category_id, dir, rule_hash, volume_id,
          journal_id, checkpoint, last_full_scan_at, status)
dirs     (id PK, path UNIQUE, target_id, mtime, file_ref)
files    (dir_id, name, ext, size, created_at, modified_at,
          accessed_at, readonly, file_ref,
          PRIMARY KEY (dir_id, name))
```

- `files` 存覆盖范围内的全部文件，分类规则在查询时应用：修改规则无需重扫，重叠的分类共享数据（基准测试 `bench_native` 采用此方式）；`dirs` 存全部子目录（用于对账）。
- 路径规范化为 `dir_id + name`，避免每行重复存储完整路径与父目录。
- `rule_hash` 由 dir、match_type、pattern、recursive 计算；规则变化只使该目标失效。
- `checkpoint` 存平台变更日志的位置（USN 或 FSEvents 事件 ID），见第 7 节。
- **索引只是缓存**：版本不符、损坏、无法打开时直接删除重建，不影响 `config.json`。
- 二级索引（扩展名、排序列）在批量写入后再建。

### 4.3 运行期

- **扫描**：`ignore::WalkBuilder::build_parallel`（关闭 gitignore / 隐藏文件过滤）或 `jwalk` 并行读目录；`filter_entry` 剪枝；先对目标目录去重与合并。
- **写入**：独立写线程，单事务批量写入，与遍历流水线并行。
- **监听**：watcher 改为监听**所有分类**的目标目录，生命周期与应用一致；窗口隐藏时继续监听、只是不推送。事件按路径防抖合并，`stat` 后在一个事务中写回，并把差异推送给前端。notify 报告溢出或需要重扫时，把目标标记为 dirty，按第 5 节第 2 级处理。
- **取消与流式**：切换分类时取消旧扫描；冷扫描按批次推送结果。
- **错误**：记录无权限的目录，而不是静默丢弃。

## 5. 重启后的三级对账

启动时**先从 SQLite 读出第一屏立即显示**，再在后台对账并推送差异。按顺序尝试，前一级不可用才降级：

| 级别 | 机制 | 适用 | 特点 |
|---|---|---|---|
| 第 1 级 | 平台变更日志回放（Windows USN / macOS FSEvents） | 本地 NTFS / APFS | 只处理关机期间的变化；能捕获内容修改；详见第 7 节 |
| 第 2 级 | 目录修改时间比对 | NTFS、APFS、ext4、btrfs、xfs | 对 `dirs` 表中每个目录 `stat`：未变则跳过，变了只重新列举这一层；新子目录遍历，消失的目录删除整棵子树 |
| 第 3 级 | 全量并行扫描 + 差异比对 | FAT32/exFAT、U 盘、网络盘、前两级失败、手动重建 | 只推送差异，界面不闪烁 |

第 2 级的局限：只修改文件内容**不会**改变目录的修改时间，因此文件集合是准确的，但大小、修改时间两列可能过期。可在界面显示后，于后台低优先级刷新这两列。

预期效果：

| 场景 | 现在 | 采用方案后 |
|---|---|---|
| 切换分类 | 全量扫描 | 查询索引，毫秒级 |
| 运行中文件变化 | 全量重扫 | 只更新变化的路径 |
| 重启后首次打开 | 全量扫描 | 立即显示；后台第 1 或第 2 级对账 |
| 修改分类规则 | 全量扫描 | 只重建该规则的索引 |
| U 盘、网络盘 | 全量扫描 | 先显示上次结果，后台第 3 级对账 |

## 6. 500 万文件规模预估与调整

### 6.1 首次索引耗时（估算，未实测）

| 平台 / 磁盘 | 冷缓存（刚开机） | 热缓存 |
|---|---|---|
| Windows + NVMe SSD | 约 30～60 秒 | 约 15～30 秒 |
| Windows + SATA SSD | 约 40～90 秒 | 约 20～40 秒 |
| Windows + 机械硬盘 | 约 5～15 分钟 | 约 1～3 分钟 |
| macOS（Apple Silicon，内置 SSD） | 约 40～90 秒 | 约 20～40 秒 |

依据：

- **Windows**：列举目录时 NTFS 一并返回大小与时间，无需逐个 `stat`。NVMe 上并行遍历约每秒 15～30 万条目。杀毒软件的过滤驱动会有额外拖慢；机械硬盘受寻道限制，并行收益有限。
- **macOS**：`readdir` 只返回文件名，需逐个 `lstat`，系统调用次数翻倍；APFS 列举本身也较慢。改用 `getattrlistbulk` 批量取元数据预计可快 1.5～2 倍（需自行实现）。
- **SQLite**：单事务预编译语句批量插入约每秒 30～80 万行，与遍历重叠，基本被掩盖。
- 对比：直接读 NTFS MFT 的工具（如 Everything）500 万文件约 5～15 秒，但需要管理员权限。

首次之后：第 1 级（USN / FSEvents）通常 1 秒以内；第 2 级约 2～10 秒。

### 6.2 此规模下必须做的调整

| 问题 | 原因 | 调整 |
|---|---|---|
| 内存放不下 | 每条 `FileEntry` 约 300 字节，500 万条约 1.5～2GB | 数据以 SQLite 为准，内存只缓存查询结果 |
| IPC 传不动 | `list_files` 一次返回全部，JSON 超过 1GB | 改为分页查询，前端按可见窗口取数 |
| 前端排序过滤扛不住 | `FileTable.tsx` 对整个数组排序过滤 | 排序、过滤、计数移到 Rust 用 SQL 完成；保留虚拟滚动，按需取数 |
| 启动显示变慢 | 读出 500 万行需 5～10 秒 | 只查第一屏（`ORDER BY 排序列 LIMIT 100`），依赖排序列索引 |
| 数据库过大 | 完整路径重复存储时约 1.5～2GB | 规范化后预计约 0.5GB；排序列索引按需添加 |
| 搜索变慢 | `LIKE '%x%'` 全表扫描约 1～3 秒 | 可选 FTS5 trigram，子串搜索几十毫秒，数据库增大 30%～50% |

其他注意事项：macOS 的 Desktop、Documents、Downloads 等受保护目录需要用户授权，否则会被跳过；Windows 系统目录的权限错误需要记录下来。

## 7. 平台原生加速层

均以第 4 节架构已实现为前提，作为第 1 级对账的加速手段。工作量按一名熟悉 Rust 与对应平台 API 的开发者估算，含测试，不含界面。

### 7.1 Windows NTFS USN Journal

USN Journal 是 NTFS 卷级、**重启后仍保留**的变更日志，记录变更原因、文件引用号与父目录引用号。保存 `journal_id` 与 `last_usn`，启动时从 `last_usn` 往后读，只处理父目录在 `dirs` 表中的记录。

| 工作项 | 估算 |
|---|---|
| **非管理员权限验证**（`FSCTL_READ_UNPRIVILEGED_USN_JOURNAL`；`OpenFileById` + `GetFinalPathNameByHandle` 还原路径） | 0.5～1 天，**必须最先做** |
| 读取日志、解析 V2/V3 记录（ReFS 为 128 位引用号） | 2～3 天 |
| 文件引用号 ↔ 路径映射（自写目录列举，用 `NtQueryDirectoryFile` 顺带取引用号） | 2～4 天 |
| 应用变更（只处理带关闭标志的记录；重命名配对；目录移入移出；硬链接） | 3～4 天 |
| 检查点与回退（日志覆盖或重建、多卷、U 盘） | 2 天 |
| 测试（NTFS / ReFS / FAT，需 Windows 虚拟机） | 2～3 天 |
| **合计** | **约 2～3 周**（前提是非管理员可读） |

**若必须管理员权限**：需要高权限辅助服务 + 进程间通信 + 安全加固，而 NSIS `currentUser` 安装无法安装系统服务，须改为按机器安装并弹出 UAC，即**改变安装模式**，再加 2～3 周。此时不建议实施。

新增依赖：`windows` crate 开启 `Win32_System_Ioctl`、`Win32_Storage_FileSystem`。

### 7.2 macOS FSEvents 历史回放（推荐）

FSEvents 按卷持久化变更记录，**普通用户可读**，覆盖所有目录。保存事件 ID 与卷 UUID，启动时从该 ID 回放；遇到"需要重新扫描子目录"标志、历史被清理或卷 UUID 变化时回退到第 2 级。

- `notify` 不支持指定起始事件 ID，需直接使用 `fsevent-sys`。
- **工作量约 3～6 天**，风险低。

### 7.3 macOS Spotlight（暂不建议）

| 工作项 | 估算 |
|---|---|
| 绑定 `MDQuery`（FFI）或 `NSMetadataQuery`（objc2） | 2～3 天 |
| glob 转 Spotlight 查询语法；正则、非递归后过滤 | 1～2 天 |
| 实时查询更新（run loop 线程、变更通知） | 2～3 天 |
| **判断覆盖范围并回退**（隐藏目录、隐私列表、外置盘、网络卷；无公开接口） | 2～4 天，风险最大 |
| 测试与调优（含索引延迟） | 2 天 |
| **合计** | **约 2～3 周**，不确定性高 |

Spotlight 主要省掉的是一次性的首次索引，却带来覆盖盲区与延迟。对"重启后不重新索引"这一目标，FSEvents 更直接可靠。若将来做文件内容搜索，再重新评估。

### 7.4 Linux

Linux 没有跨发行版统一的索引系统：

- `locate` 系列（mlocate / plocate）：定时重建、非实时、只有路径，不一定默认安装。
- GNOME Tracker（LocalSearch）/ KDE Baloo：依赖桌面环境，接口各异，默认只索引用户目录。
- inotify：不能递归、受 `max_user_watches` 限制；fanotify 整盘监听需要 `CAP_SYS_ADMIN`；二者重启后都不保留。
- 没有通用、持久、普通用户可读的变更日志（btrfs / ZFS 的机制需要 root 且限定文件系统）。

因此若将来支持 Linux，使用第 4 节架构 + 第 2、3 级对账即可。FileDock 目前未正式支持 Linux。

### 7.5 汇总

| | 工作量 | 主要风险 | 收益 |
|---|---|---|---|
| 第 2 级对账（所有平台） | 含在第 4 节中 | 内容修改导致元数据过期 | 重启后秒级对账 |
| macOS FSEvents 回放 | 3～6 天 | 低 | 重启后只处理变化 |
| Windows USN | 2～3 周 | 权限；可能需改安装模式 | 重启后只处理变化，含内容修改 |
| macOS Spotlight | 2～3 周 | 覆盖盲区、延迟 | 省掉首次索引 |

## 8. 基准测试

已实现为 Cargo example，位于 [`app/src-tauri/examples/`](../app/src-tauri/examples/README.md)，依赖只在 `[dev-dependencies]` 中，不进入安装包。使用方法见该目录的 README。

### 8.1 程序

| example | 内容 |
|---|---|
| `bench_current` | 基线：直接调用 app 的 `scan.rs`，每次都全量遍历 |
| `bench_seekr` | 方案 1：seekr 公开 API（从 GitHub 固定到 `f11bc11`），缺的能力用标注 `GLUE:` 的胶水代码补上 |
| `bench_native` | 方案 2：`ignore` 并行遍历 + `notify` + SQLite，含第 2、3 级对账；可切换 `walkdir`、FTS5 |
| `bench_spotlight` | 方案 3：CoreServices `MDQuery`（仅 macOS） |
| `bench_dataset` / `bench_compare` | 数据集生成、离线修改与还原；汇总对比表 |

规则匹配与标准答案通过 `#[path]` 直接引入 app 的 `matcher.rs`、`scan.rs`，与 app 行为一致。数据集、索引和报告放在仓库外的 `~/FileDockBench`。

### 8.2 场景

| 场景 | 测量内容 | 对应问题 |
|---|---|---|
| S1 首次索引 | 总耗时、内存峰值、索引大小 | 首次成本 |
| S2 列出分类 | 按"目录 + 规则 + 是否递归"取总数和第一屏 100 条 | 切换分类慢 |
| S3 分类内搜索 | 名称子串搜索延迟（`LIKE` 与可选 FTS5） | 搜索框 |
| S4 运行中增量 | 新建 500 个文件、改 / 重命名 / 删、删除整个目录后，索引反映的延迟 | 变化后全量重扫 |
| S5 离线变更后重启 | 退出后修改 1% 文件，重启到一致状态的耗时 | 重启后重新索引 |
| S6 正确性 | 与 `scan.rs` 结果比对：缺少、多出、大小过期 | 各方案暗坑 |

冷缓存：macOS 手动执行 `sudo purge`；Windows 需重启或用 RAMMap 清空 standby 列表。

### 8.3 与计划的差异

- 位置从仓库根目录改为 `app/src-tauri/examples/`，以便 `cargo run --example` 直接识别；seekr 改为 GitHub 依赖，方便在 Windows 机器上运行。
- 新增 `bench_current` 基线，衡量现状。
- Spotlight 的 S4 用同步查询轮询，而不是 `kMDQueryWantsUpdates` 实时通知：衡量的是系统索引反映变化的延迟，与通知机制无关。
- 实测发现 Spotlight 查询语言里单独的 `"*"` 匹配不到任何文件，"全部文件"改用 `kMDItemContentTypeTree == "public.item"`。

### 8.4 冒烟测试结果（2 万文件，仅供参考）

Apple M3，热缓存，2 万个文件、505 个目录。规模太小，**不能用于选型**，只用来确认程序可用、各方案的特征与分析一致：

| 指标 | current | seekr | native | spotlight |
|---|---|---|---|---|
| S1 首次索引 | 无索引 | 274 ms | 44 ms | 已被系统索引，0.6 s 确认 |
| S1 索引占用磁盘 | — | 15.2 MB | 2.0 MB | — |
| S2 列出全部 2 万个文件 | 63 ms | 22 ms | 9 ms | 132 ms（只返回 15,843 个） |
| S4 新建 500 个文件后反映 | 57 ms（一次全量扫描） | 710 ms | 176 ms | 2.7 s |
| S5 重启后追平 | 无索引 | 213 ms | 9 ms | 系统维护，约 2.7 s 后可见文件一致 |
| S6 追平后正确性 | ✓ | 缺 43 个（重命名的文件） | 47 个文件大小过期（原地修改） | 隐藏目录中的 4,165 个文件缺失 |

已确认的特征：

- seekr 的 `index_incremental` 只收录修改时间更新的文件，**重命名的文件在重启后丢失**。
- native 第 2 级对账的已知局限（原地修改后大小过期）如实出现；第 3 级（`--resume-mode full`）没有该问题，2 万文件耗时 26 ms。
- Spotlight **完全不索引隐藏目录**（`.git` 下的全部文件），列表和搜索延迟也比 SQLite 高一个数量级。

正式结论需要在 10 万、100 万规模以及 Windows 机器上运行后得出。

### 8.5 环境

参考开发机：Apple M3，24GB 内存，macOS 26.4.1，rustc 1.95.0（满足 seekr 对 rustc ≥ 1.88 的要求）。Windows 测试需另备机器。

## 9. 实施路线

1. **存储层 + 启动先显示**：SQLite 表结构、规则失效、启动时查询第一屏（仅第 3 级对账）。完成后重启首屏即为瞬时。
2. **watcher 增量写回**，改为监听所有分类。
3. **分页查询**：排序、过滤、计数移到 Rust；前端按可见窗口取数。
4. **第 2 级对账**（目录修改时间比对）。
5. **macOS FSEvents 回放**。
6. **Windows USN 权限验证**：通过后投入实现，不通过则保持第 2 级。
7. Spotlight 暂不实施。

改动集中在 [`scan.rs`](../app/src-tauri/src/scan.rs)、[`watch.rs`](../app/src-tauri/src/watch.rs)、[`commands.rs`](../app/src-tauri/src/commands.rs)、[`App.tsx`](../app/src/App.tsx)、[`FileTable.tsx`](../app/src/components/FileTable.tsx)。新增依赖：`rusqlite`（bundled）、`ignore` 或 `jwalk`；第 5、6 步另需 `fsevent-sys` 与 `windows` crate 相应 feature。
